Analyzes the architecture of OpenSandbox. OpenSandbox is a sandbox platform for running untrusted workloads, such as code generated by AI agents, in isolated environments, and it abstracts the sandbox lifecycle behind a REST API. OpenSandbox supports both a Docker runtime running on a single host and a Kubernetes runtime, but since the Docker runtime is intended for development and single-host PoC use, this article analyzes the Kubernetes runtime. The analysis is based on v1.2.1.

## 1. Architecture

{{< figure caption="[Figure 1] OpenSandbox Architecture" src="images/opensandbox-architecture.png" width="1000px" >}}

[Figure 1] shows the architecture when OpenSandbox is deployed on Kubernetes. OpenSandbox consists of the following components.

* **Server** : The component that provides the sandbox lifecycle REST API. It receives sandbox create/exec/terminate requests through the SDK or REST API and manages sandboxes by creating Kubernetes custom resources. Its configuration is injected as a TOML-format ConfigMap, and since multi-replica HA is not supported, it runs as a single replica.
* **Controller** : A Kubernetes operator that reconciles the **BatchSandbox**, **Pool**, and **SandboxSnapshot** custom resources created by the server and manages the actual sandbox pods.
* **Base** : A component that installs only cluster-scoped resources such as OpenSandbox CRDs and RBAC. Since it has no workloads, it is installed only once per cluster.
* **Ingress Gateway** (Optional) : A proxy that relays traffic destined for sandboxes. The server only returns the gateway address to clients, and actual sandbox traffic is delivered to sandboxes through the gateway.
* **Node Agent** (Optional) : A DaemonSet that collects sandbox container logs on each node.
* **Fast Sandbox** (Optional) : A separate control plane and node runtime that provides a Firecracker microVM-based fast sandbox execution path.

The key characteristic of the OpenSandbox architecture is that it **keeps the lifecycle API as a fixed point and adds execution models underneath as layers**. The API used by clients stays the same, and how a sandbox is actually executed is determined by three orthogonal axes in the server configuration: the runtime (`runtime.type`), the workload provider (`workload_provider`), and the secure runtime (`secure_runtime`). New features are added through the **OSEP** (OpenSandbox Enhancement Proposal) process, similar to Kubernetes KEPs, and in fact the agent-sandbox workload provider and the Fast Sandbox execution path were added over successive versions.

## 2. Namespace Trust Boundary

OpenSandbox is designed on the premise of separating namespaces by the nature of the components.

* **Control Plane Namespace** : The namespace where platform components such as the server, controller, and ingress gateway run. Secrets such as API keys and signing keys are also located in the control plane namespace.
* **Sandbox Workload Namespace** : The namespace where actual sandbox pods are created, specified by `[kubernetes].namespace` in the server configuration. The Helm chart does not create the sandbox workload namespace, so it must be created separately.

Since untrusted user code runs directly in sandbox pods, the core reason for this separation is to avoid placing control plane secrets and sandbox workloads in the same namespace. Because the sandbox workload namespace is an execution space for untrusted code, it is also the place to apply Kubernetes-level guardrails such as resource limits via LimitRange/ResourceQuota and baseline blocking via NetworkPolicy.

## 3. Sandbox Execution Paths

{{< figure caption="[Figure 2] OpenSandbox Sandbox Execution Paths" src="images/opensandbox-execution-paths.png" width="1000px" >}}

[Figure 2] shows the three paths through which sandboxes are executed on the Kubernetes runtime. The workload provider is an exclusive setting where only one can be selected per server, but Fast Sandbox is a separate path that is served alongside, depending on the request content, regardless of the workload provider.

```toml {caption="[Text 1] Execution path related settings in the server config.toml"}
[runtime]
type = "kubernetes"

[kubernetes]
namespace = "opensandbox"                  # Sandbox workload namespace
workload_provider = "batchsandbox"         # batchsandbox or agent-sandbox
fastpath_endpoint = "fast-sandbox-fastpath.opensandbox-system.svc:9090"  # Fast Sandbox path
```

[Text 1] shows the settings in the server config.toml that determine the execution path. Which workload provider to use and whether the Fast Sandbox path is enabled are both determined by server configuration, while the API format used by clients stays the same regardless of the execution path.

### 3.1. BatchSandbox Provider

The default workload provider. When the server creates a BatchSandbox custom resource, which is OpenSandbox's own CRD, the controller creates the sandbox pod. **execd**, which is responsible for in-sandbox bootstrap, is injected into the sandbox pod as init, and the code execution (exec) API is handled through execd. This is the first-class path where most of OpenSandbox's features are provided, including volume (PVC) lifecycle management, egress restriction, and snapshot-based pause/resume.

### 3.2. agent-sandbox Provider

A workload provider that delegates sandbox pod management to the Kubernetes SIG [agent-sandbox](https://github.com/kubernetes-sigs/agent-sandbox) controller. The server creates a Sandbox custom resource in the agents.x-k8s.io group instead of a BatchSandbox custom resource, and the agent-sandbox controller is responsible for the pod lifecycle. Since pause/resume is also implemented by patching the `spec.operatingMode` field of the Sandbox custom resource, it has the characteristic that pod removal/recreation style pause/resume is possible without a container registry for snapshots. On the other hand, features of the BatchSandbox provider such as egress restriction and per-request PVC lifecycle management are not provided.

### 3.3. Fast Sandbox

A Firecracker microVM-based fast execution path. When a sandbox creation request includes a `templateId`, the server creates the sandbox through **FastPath**, Fast Sandbox's gRPC control plane, instead of the workload provider. The sandbox runs as a Firecracker microVM inside a worker pod called a **Fastlet**, not as a Kubernetes pod, and provides millisecond-level startup time by restoring a pre-built golden image snapshot. Nodes with KVM available are required.

### 3.4. Execution Path Comparison

| | BatchSandbox | agent-sandbox | Fast Sandbox |
|---|---|---|---|
| Execution unit | Pod | Pod | MicroVM inside a Fastlet pod |
| Sandbox manager | OpenSandbox Controller | agent-sandbox Controller | Fast Sandbox Control Plane (FastPath) |
| Selection | `workload_provider` | `workload_provider` | `templateId` in the request (alongside the provider) |
| Startup time | Pod creation + container start | Pod creation + container start | Snapshot restore (milliseconds) |
| Pause/Resume | Rootfs snapshot commit (registry required) | Pod removal/recreation (no registry) | Live snapshot (including memory, node local) |
| Egress restriction | Supported | Not supported | Separate profile |
| Special requirements | - | agent-sandbox controller installed | KVM nodes, artifact store |

The detailed behavior of the BatchSandbox and agent-sandbox providers is analyzed in the [OpenSandbox BatchSandbox](../opensandbox-batch-sandbox/) article, and the detailed behavior of Fast Sandbox in the [OpenSandbox Fast Sandbox](../opensandbox-fast-sandbox/) article.

## 4. Lifecycle API

The lifecycle API provided by the server exposes the same endpoints regardless of the execution path, and only the internal implementation differs depending on the execution path.

* **Create** : Creates a sandbox. It supports container image-based creation (`image`) and Fast Sandbox template-based creation (`templateId`), and per-sandbox specs such as volumes, egress policy (`networkPolicy`), and idle policy are declared together.
* **Exec** : Executes code inside the sandbox. It is handled by execd injected into the sandbox pod.
* **Timeout / Renew** : Every sandbox has a lifetime (`timeout`) at creation time, and it can be extended through the renew API or access-based automatic renewal (OSEP-0009). The server configuration `max_sandbox_timeout_seconds` can enforce an upper bound on the timeout in creation requests.
* **Pause / Resume** : Transitions a sandbox into an idle state to release compute resources, and later resumes with the same `sandboxId`. As shown in [Text 2], the implementation and preservation scope differ per execution path.

```text {caption="[Text 2] Pause/Resume semantics per execution path"}
BatchSandbox  : Commits the rootfs as an OCI image, pushes it to a registry, then removes the pod
                (filesystem preserved, processes restarted)
agent-sandbox : Removes only the pod by patching operatingMode on the Sandbox custom resource
                (only PVC data preserved)
Fast Sandbox  : Stores a microVM memory checkpoint on the node locally
                (memory/processes preserved, automatic idle-pause/wake supported)
```

[Text 2] shows how the same pause/resume API is implemented differently per execution path. Even with an identical API, the preserved scope differs — filesystem, PVC data, or memory — so clients must be aware of the semantic differences of the execution path the server uses.

Authentication uses API keys via the `OPEN-SANDBOX-API-KEY` header, and a multi-tenant configuration that provides separate API keys per tenant is also supported through the `[tenants]` configuration. If no API key is configured, the server does not start without explicit risk acknowledgment.

## 5. Ingress Path

{{< figure caption="[Figure 3] OpenSandbox Ingress Gateway Request Path" src="images/opensandbox-ingress.png" width="900px" >}}

[Figure 3] shows the path a client request takes through the ingress gateway to reach a sandbox in gateway mode. The ingress path for accessing HTTP servers running inside sandboxes operates in two ways depending on the `[ingress].mode` setting.

* **direct** : The server directly returns the sandbox address, and the client accesses the sandbox directly.
* **gateway** : The server returns the ingress gateway address, and client requests are relayed to the sandbox through the gateway. The gateway finds the target sandbox based on route information included in a header or the URI.

In gateway mode, route information tampering can be prevented through **OSEP-0011 Secure Access**. The server and gateway share an HMAC-SHA256 signing key ring, and the gateway verifies route tokens signed by the server. Since the key ring supports multiple keys and an active key designation, zero-downtime key rotation is possible. Signing keys are injected as environment variables through Kubernetes Secrets, designed so that key material is not exposed in configuration files or pod args.

Because the gateway is positioned as the single entry point for sandbox traffic, it also performs roles beyond ingress relay. In Fast Sandbox's idle-pause/wake-on-access (OSEP-0024), the gateway is both the activity source that records each sandbox's last activity time and the wake actor that parks requests headed to a paused sandbox until restoration completes.

## 6. Egress Boundary

{{< figure caption="[Figure 4] OpenSandbox Egress Enforcement Chain" src="images/opensandbox-egress.png" width="900px" >}}

[Figure 4] shows the enforcement chain for egress traffic leaving a sandbox. Egress traffic from code inside a sandbox is controlled through an **egress sidecar** injected into the sandbox pod. The egress sidecar is injected only when the sandbox creation request includes a `networkPolicy`, and provides three levels of enforcement depending on the `[egress].mode` setting.

| Mode | Enforcement | Characteristics |
|---|---|---|
| `dns` | DNS proxy | Domain-level allow/deny. IP/CIDR rules are not enforced |
| `dns+nft` | DNS proxy + nftables | IP/CIDR-level blocking in addition to domain level |
| `forward` | CONNECT relay | Forces all TCP connections of all sandboxes through a designated upstream proxy. The sidecar is injected into every sandbox regardless of `networkPolicy` |

What is notable about egress enforcement is the **bootstrap order designed with untrusted code as the premise**. On Kubernetes, the `egress-init` init container installs a default-deny nftables fence before the workload container starts, and once the egress sidecar completes initialization, it atomically replaces the fence with the actual policy. This blocks sandbox code from reaching outside using the time gap before sidecar initialization. This is a point that distinguishes it from service mesh sidecar injection, which presumes cooperative workloads.

The detailed spec of per-sandbox `networkPolicy`, along with volumes and snapshots, is analyzed in the [OpenSandbox BatchSandbox](../opensandbox-batch-sandbox/) article.
